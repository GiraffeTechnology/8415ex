# Original direct-return reserved task composition

WalletDirectReturnTask composes the existing original EX rollback binding with
the existing reserved Wallet exact-task gateway. The operation remains one
ERC-721 transfer from the original current owner to the effective-holder
boundary, with the same NFT, receipt, refused leg and original ordered affected
interval. It does not traverse intermediate wallets or substitute returnHop.

The installed trusted application supplies its original task digest, child
digest, Wallet operation ID and EX native/journal scope. These identities remain
distinct and are never hashed or converted into each other. The composition
does not authenticate arbitrary request-supplied mappings. The original source
must establish the exact task/operation relationship; original EX authority,
effective-holder ordering and original Wallet execution-time checks remain
necessary technical duties. A structurally bound plan is not that evidence.

execute forwards the original four-field request through the original client.
There is no additional status preflight, prepare, authorize, reserve, new grant,
login, all-ready or human approval step. The original server retains its task,
reservation and budget-revision CAS; the original client retains its persistent
attempt guard. Reconstructing this object does not create or clear a store.
An exception propagates without resend, and a returned HTTP body leaves the
native result unknown. No second principal debit or automatic refund is added.

read is an independent original status observation. A missing reservation stays
not-observed, never authenticated native absence; it cannot be used as the None
absence port required by DurableEXOperationJournal.invoke_once. A cancelled,
submitted or unknown task is not proof of asset return, Oracle registration,
principal settlement or recovery completion. Private binding data is not a
frontend projection.

This stage depends on the reserved-task gateway stage and the merged original
direct-return binder. Its integration base preserves current main source plus
the six unchanged original status/gateway blobs, using a two-parent Git commit.
Only three new files implement/document this composition; prior source stages
are reused, not reimplemented. Eight authored synthetic definitions cover
exact request forwarding, no extra requests, boundary/interval mismatch,
detached inputs, unknown/missing observations, durable resend protection and
distinct native/task identities. Tests have not been run by the author. Actual
native mapping, protected-prefix atomicity, funds and chain acceptance remain
open.
