# Three registration-source read and detail contracts

The source keys REG-DIRECT, REG-ELECTRONIC and REG-INTERMEDIARY map explicitly to the existing domain paths REG_DIRECT, REG_ELECTRONIC and REG_INTERMEDIARY. They describe simulated registrar roles, not spot/futures/leverage modes or real institutional partnerships. A source must match the receipt's existing mint-declared path and non-empty voucher format/version/required fields before an original task is read. Unknown source, missing format, duplicate fields or unavailable original binding are refused rather than rerouted.

All three use the same supplied OriginalTaskJournalReader and therefore the same original get-only runtime entry. There is no source-specific financial backend, Oracle copy, journal, settlement coordinator or second receipt. The resolver must load an authenticated existing mint/task binding for the currently authorized operator; fixture data is not such a proof. No raw off-chain voucher is accepted or verified in EX and no holder is changed independently.

The read-only choice form targets an explicitly supplied existing same-origin route. A mounted authenticated host must parse scalar source/receipt parameters, apply its existing session/grant protections and no-store response policy, then call render_source. Each detail provides the source explanation, mint-declared format, original native operation/status/revision/update/transaction identity and separate Oracle/owner-holder/principal/gas evidence dimensions. Where no actual authoritative binding has been supplied, UNBOUND or NOT_VERIFIED remains visible. Original accepted/confirmed task status cannot become EX registration or payment completion. The view signs nothing, freezes/releases nothing and never advances a transaction.

This is executable controller/rendering source, not an installed UI or three-path acceptance report. It is the initial read/status portion of the middle/frontend integration. Actual source task creation through the original approved runtime, Oracle chain-record consumption, common order/wallet/gas/owner-holder/funding/history joins, server route mounting and real per-source UI/provider tests remain outstanding. Do not call the complete three-source or whole-artwork backend alignment requirement passed from these functions. The same underlying whole-artwork fill-time payment difference recorded by the parent reader still needs an exact native settlement mapping.

Seven authored unittest methods cover the shared original get backend across all sources, wrong mint-path refusal, unknown source/receipt refusal before binding, invalid format refusal, per-source provenance and separate unknown evidence, explicit same-origin read choices and resolver failure without fallback/data leakage. Validation command: python -m unittest integration.test_original_task_journal_reader integration.test_registration_source_workbench -v. All tests, original service/Oracle calls, installed browser/UI, wallet/deployment/chain and full backend alignment remain NOT_RUN at initial submission. Existing workbench, producer modules and submitted source files are unchanged.
